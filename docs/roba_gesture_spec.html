roBa Trackball Gesture 仕様書

対象: roBa / ZMK / Windows・macOS 両対応キーマップ

Draft トラックボールを使ったジェスチャーレイヤー仕様。Windows と macOS で、できるだけ同じ物理操作から同じ意味の挙動を得ることを目的とする。

1. 目的

roBa のトラックボールを、通常のポインティング・スクロール操作に加えて、ウィンドウ操作やタブ操作のジェスチャー入力として利用する。

既存の mac レイヤー / Windows レイヤー構成を活用し、同じキー・同じトラックボール操作で OS ごとのショートカット差分を吸収する。

2. レイヤー構成

本リポジトリのキーマップは「mac ベースレイヤー（LAYER_BASE）＋ Windows 用トグルオーバーレイ（LAYER_DEFAULT_WIN）」という構成で、Windows は独立したベースレイヤーではなく &tog で被せるトグル状態として扱う。 そのため、ジェスチャーレイヤーは OS ごとに 4 枚へ分けず、機能ごとに 2 枚（ウィンドウ / タブ）に集約し、OS 差分はジェスチャーエンジン（C 実装）側で吸収する。 

LAYER_BASE         (mac ベース)
LAYER_DEFAULT_WIN  (Windows トグルオーバーレイ)

WINDOW_GESTURE     (ウィンドウ操作・OS共通)
TAB_GESTURE        (タブ操作・OS共通)

2.1 OS 判定

ジェスチャーエンジンは、発火するキーコードを送信する直前に Windows トグルレイヤーの活性状態を見て OS を判定する。

if zmk_keymap_layer_active(LAYER_DEFAULT_WIN):
    os = WINDOWS
else:
    os = MACOS

ジェスチャーレイヤー自体は OS 共通のままにし、同じ物理操作から OS ごとのショートカットを送り分ける。これにより、レイヤー枚数と遷移キー、キーマップ重複を最小化できる。物理キーの割り当てはキーマップ側の実装詳細として扱う。

2.2 レイヤー遷移

ジェスチャーレイヤーへの移動キーは本仕様では固定しない。ベースレイヤー（mac / Windows いずれのトグル状態でも）から、共通の WINDOW_GESTURE / TAB_GESTURE へ移動する。

遷移先用途OS 差分の扱い
WINDOW_GESTUREウィンドウ / アプリ切り替えエンジンが OS 判定して送信
TAB_GESTUREタブ操作エンジンが OS 判定して送信

2.3 実装方式

ジェスチャー判定は ZMK のカスタム input-processor（C 実装）として追加する（既存の behavior_mkp_quick_exit と同じく、src/ 配下のモジュール + Kconfig + dts/bindings 構成）。 この processor を trackball_listener の input-processors チェーンに挿入し、ジェスチャーレイヤーが活性なときだけトラックボールの相対移動イベントを処理する。

3. 共通ジェスチャー判定仕様

3.1 入力開始

ジェスチャーレイヤー中にトラックボールの移動量が最小閾値を超えた時点で、ジェスチャー入力を開始する。

if abs(dx) + abs(dy) > start_threshold:
    gesture_active = true

ジェスチャーレイヤーが活性な間は、トラックボールの相対移動イベント（X / Y）をジェスチャーエンジンで消費し、後段へ伝播させない（input-processor は ZMK_INPUT_PROC_STOP 相当を返す）。 これにより、ジェスチャー中にポインタが動いたり、オートマウス用の zip_temp_layer（trackball_listener の処理）が LAYER_MOUSE を被せてしまうのを防ぐ。 ジェスチャーレイヤーが非活性のときは、従来どおり通常のポインタ入力として素通しする。

3.2 終了タイミング

終了判定はジェスチャー種別で異なる。

  • 単発（上下）: トラックボールが stop_timeout の間停止したら確定（1回発火）。確定後はレイヤーを保持したまま次の単発ジェスチャーを待機する。レイヤーキーを離した時点で未確定なら、その時点で確定する。
  • 連続（左右）: トラックボール停止では終了せず、レイヤーキーを離した時点で終了する。保持していた修飾キーはこのとき解放され、選択が確定する（Alt-Tab / Cmd-Tab / Ctrl-Tab を開いたまま行き来し、離して確定するのと同じ操作感）。

初期値の目安:

項目推奨初期値
start_threshold10〜20 カウント
stop_timeout80〜120 ms（単発の確定に使用）
direction_ratio2.0
step_threshold60〜80 カウント

3.3 4方向強制判定

斜め入力による誤爆を避けるため、方向は上下左右の4方向に限定する。

if abs(dx) > abs(dy) * direction_ratio:
    direction = RIGHT if dx > 0 else LEFT
elif abs(dy) > abs(dx) * direction_ratio:
    direction = DOWN if dy > 0 else UP
else:
    direction = NONE

direction = NONE の場合は、ジェスチャーを発火しない。

上記の dx>0=RIGHT / dy>0=DOWN はあくまで論理上の定義。roBa の PMW3610 は実装上の取り付け向きにより軸が回転・反転している場合があるため（スクロール方向を Windows / mac で別エンコーダにしているのと同根の問題）、方向判定はトラックボールの実装座標に合わせて実機キャリブレーションする。必要なら符号反転や軸入れ替えのオフセットをエンジン側に持たせる。

4. 移動量と連続操作

左右ジェスチャー（連続）は、トラックボールのX方向の正味移動量に追従して双方向にステップする。連続モードに入った時点でまず 1 ステップ発火し、以降は step_threshold 進むごとに 1 ステップ。上限はなく、転がした分だけ進む。

右へ進んだ後に左へ戻すと、戻した分だけ逆方向（Shift+Tab 等）が送られ、左右の往復ができる。これによりスイッチャ上で候補を行き来して選び直せる。

4.1 ステップ判定（双方向・アンカー方式）

// 連続モード開始時
mod down
anchor_x = accum_x
emit 1 step (開始方向)

// 以降、移動のたびに
while accum_x - anchor_x >= step_threshold:   // 右へ
    emit forward (例: Tab)
    anchor_x += step_threshold
while accum_x - anchor_x <= -step_threshold:  // 左へ（戻し）
    emit backward (例: Shift+Tab)
    anchor_x -= step_threshold
項目推奨初期値
step_threshold60〜80 カウント

旧仕様の「クイックフリック判定（時間ベース）」と「最大ステップ数(max_steps)」は廃止。開始時の即時 1 ステップでフリック1回切替の操作感を保ちつつ、移動距離に正比例した上限なしの双方向ステップに統一した。

4.2 挙動例

入力結果
右へ少し転がして離す右方向 1 ステップ（フリック1回切替）
右へ転がし続ける（保持）step_threshold ごとに 1 ステップ、上限なし
右へ3ステップ→左へ2ステップ戻すTab×3 の後 Shift+Tab×2（差し引き1つ先で確定）
少しだけ動かす (< start_threshold)閾値未満なら無視
斜めに動かす（方向が曖昧）無視（4方向強制）

5. ウィンドウジェスチャーレイヤー

目的: アプリ切り替え、タスクビュー、デスクトップ表示をトラックボールで行う。

5.1 割り当て

方向WindowsmacOS意味連続移動
↑Win + TabCtrl + Up全体表示 (Task View / Mission Control)なし
↓Win + DCtrl + DownWindows: デスクトップ表示 / macOS: App Exposé（現在アプリのウィンドウ一覧）なし
→Alt Down → Tab × N → Alt UpCmd Down → Tab × N → Cmd Up次のアプリあり
←Alt Down → Shift+Tab × N → Alt UpCmd Down → Shift+Tab × N → Cmd Up前のアプリあり

macOS は Mission Control の既定ショートカット Ctrl + Up（全体表示）/ Ctrl + Down（App Exposé）を用いる。いずれも既定で有効だが、システム設定 → キーボード → ショートカット → Mission Control で無効化されていないことを確認する。なお Windows の ↓（Win + D）はデスクトップ表示、macOS の ↓（App Exposé）は現在アプリのウィンドウ一覧表示で、厳密には意味が異なる点に注意する。

5.2 Alt / Cmd の保持

Windows の Alt+Tab、macOS の Cmd+Tab は、修飾キーを押したまま Tab（戻しは Shift+Tab）を送信し、レイヤーキーを離した時点で修飾キーを離す。

gesture start (連続モード開始):
    modifier down   // Windows: Alt, macOS: Cmd

while レイヤー保持中:
    右へ転がす → Tab、左へ戻す → Shift+Tab（双方向・上限なし）

レイヤーキー解放:
    modifier up   // ここで選択確定

これにより、アプリ切り替え UI を開いたまま候補を左右に行き来し、レイヤーキーを離して選択を確定できる。トラックボール停止では終了しない。

6. タブジェスチャーレイヤー

目的: ブラウザ、VS Code、Cursor、Finder/Explorer などでタブ操作を共通化する。

6.1 割り当て

方向WindowsmacOS意味連続移動
↑Ctrl + TCmd + T新規タブなし
↓Ctrl + WCmd + Wタブを閉じるなし
→Ctrl Down → Tab × N → Ctrl UpCtrl Down → Tab × N → Ctrl Up次のタブあり
←Ctrl Down → Shift+Tab × N → Ctrl UpCtrl Down → Shift+Tab × N → Ctrl Up前のタブあり

macOS でもブラウザや VS Code のタブ切り替えは多くの場合 Ctrl+Tab / Ctrl+Shift+Tab が使える。ただしアプリによっては Cmd+Shift+[ / Cmd+Shift+] の方が自然な場合がある。

6.2 Ctrl の保持

タブ切り替え（→ / ←）も、ウィンドウジェスチャー（5.2）と同様に Ctrl を押したまま Tab を複数回送信し、停止判定時に Ctrl を離す修飾キー保持モデルを採用する。 

gesture start:
    Ctrl down

while gesture active:
    send Tab or Shift+Tab according to step count

gesture stop:
    Ctrl up

修飾保持は意図的な設計であり、単に Ctrl+Tab を N 回送るのとは挙動が異なる。VS Code / Cursor、および MRU 切り替えを有効にした Firefox などでは、Ctrl を保持している間だけ「最近使用順（MRU）の切り替え UI」が開き、Ctrl を離した時点で選択が確定する。これはウィンドウ切り替えの Alt / Cmd 保持と同じ操作感で、切り替え中の候補が視覚的に分かるという利点がある。新規タブ（↑）/ タブを閉じる（↓）は単発なので保持しない。

7. 実装上の状態管理

ジェスチャー処理は、最低限以下の状態を持つ。

mode: NONE | SINGLE | CONTINUOUS
accum_dx: int
accum_dy: int
anchor_x: int                 // CONTINUOUS: 直近ステップ境界の accum_dx
held_modifier: NONE | ALT | CMD | CTRL

7.1 疑似コード

on_trackball_move(dx, dy):
    if not in_gesture_layer:
        pass through as normal pointer input
        return

    accum_dx += dx ; accum_dy += dy

    if mode == NONE and abs(accum_dx) + abs(accum_dy) > start_threshold:
        direction = resolve_4way(accum_dx, accum_dy)
        if direction in [LEFT, RIGHT]:
            mode = CONTINUOUS
            modifier_down()              // レイヤー解放まで保持
            anchor_x = accum_dx
            emit_step(direction)         // 開始時に即 1 ステップ
        elif direction in [UP, DOWN]:
            mode = SINGLE
        else:
            return                       // 方向が曖昧なら待機

    if mode == CONTINUOUS:               // 双方向・上限なし
        while accum_dx - anchor_x >= step_threshold:
            emit_forward() ; anchor_x += step_threshold
        while accum_dx - anchor_x <= -step_threshold:
            emit_backward(); anchor_x -= step_threshold
    elif mode == SINGLE:
        reschedule_stop_timer(stop_timeout)

on_stop_timer():                          // SINGLE のみ確定
    if mode == SINGLE:
        emit_single_action(resolve_4way(accum_dx, accum_dy))
        reset_gesture_state()             // 保持したまま次の単発を待機

on_layer_deactivate(layer):               // レイヤーキー解放 = 連続の終了点
    if layer is a gesture layer:
        if mode == SINGLE: emit_single_action(...)   // 停止前に離した場合の取りこぼし防止
        release_held_modifier_if_any()    // ここで選択確定／押しっぱなし防止
        reset_gesture_state()

連続（左右）はレイヤーキー解放で終了・修飾解放する。修飾キー（Alt / Cmd / Ctrl）を保持したままレイヤーが非活性化されたら必ず解放し、状態をリセットする（押しっぱなし事故の防止と選択確定を兼ねる）。単発（上下）はトラックボール停止で確定する。

8. OS判定ミス時の安全性

OS の送り分けは Windows トグルレイヤー（LAYER_DEFAULT_WIN）の活性状態で判定する（2.1）。実際に接続している OS とトグル状態が食い違っていると、OS に合わない修飾キー組み合わせが送信される。今回の用途では、基本的にはアプリ切り替え、タスクビュー、デスクトップ表示、タブ操作に限定されるため、ファイル削除や送信などの重大な破壊的操作には直結しにくい。

誤操作パターン想定される結果リスク
macOS 接続中に Windows トグルが ONWindows 用の Win / Alt 組み合わせが macOS で Command / Option として扱われ、意図しない OS ショートカットが発火する可能性がある。中
Windows 接続中に Windows トグルが OFFmacOS 用の Cmd / Ctrl+Up などが Windows で別動作となり、アプリ切り替えやデスクトップ表示が意図とずれる可能性がある。中
タブを閉じる操作の誤発火ブラウザやエディタの現在タブが閉じる。多くの場合は再オープン可能だが、未保存編集がある場合は注意が必要。中
左右連続操作の誤発火アプリやタブが複数個切り替わる。低〜中

安全性を高めるため、ジェスチャーレイヤーには削除、送信、保存せず閉じる、強制終了、ログアウト、スリープ、電源操作などの破壊的・状態変更の大きい操作を割り当てない。

8.1 安全設計の指針

  • 上下方向のうち、特に下方向には破壊的操作を置かない。
  • タブを閉じる操作は便利だが、誤操作が気になる場合は別レイヤーまたは通常キーに退避する。
  • OS（Windows トグル）状態を確認しやすいように、Bluetoothプロファイル、LED、OLED、または明示的なレイヤー切り替えキーを併用する。
  • 修飾キー保持中にレイヤーを抜けても押しっぱなしにならないよう、レイヤー非活性化時に必ず修飾キーを解放する（7.1）。
  • 初期実装では「表示・切り替え」系に限定し、慣れてから「閉じる」系を追加する。

9. 設計方針

  • 長フリック・短フリックの別機能化はしない。誤操作を避けるため、機能差ではなく移動ステップ数の差に限定する。
  • ジェスチャー終了はレイヤーキー解放ではなく、トラックボール停止で判定する。
  • 左右方向は連続移動に対応する。
  • 上下方向は単発操作に限定する。
  • 斜め方向は無視し、4方向に強制する。
  • OS差分はレイヤーを分けず、ジェスチャーエンジン側で Windows トグル状態を見て送り分ける（2.1）。
  • ジェスチャー判定はカスタム input-processor（C 実装）として追加し、レイヤー活性時のみトラックボール移動を消費する（2.3 / 3.1）。

10. 初期実装の推奨範囲

  1. カスタム input-processor の雛形を追加し、ジェスチャーレイヤー活性時にトラックボール移動を消費（カーソル停止）できることを確認する。
  2. 方向判定（4方向強制）を実機キャリブレーションする。
  3. WINDOW_GESTURE を実装する（↑ / ↓ を単発、← / → を修飾キー保持型の連続移動）。
  4. OS 判定（Windows トグル状態）による送り分けを実装する。
  5. TAB_GESTURE を追加する。
  6. レイヤー非活性化時の修飾キー解放（安全策）を実装する。
  7. 閾値（start_threshold / stop_timeout / step_threshold など）を実機で調整する。
